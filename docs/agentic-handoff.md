## Design questions blocking backend integration

Read this first. These four are product, UX or backend decisions, not wiring tasks. Each blocks part of the [wiring checklist](#8-wiring-checklist), and none can be solved in the REST layer alone.

### A. Approvals happen inside a live session, and are denied when nobody is watching

- **Prototype model.** A started run reaches `AwaitingApproval`; the application shows `actionRequired` as its inventory next action; anyone can approve or reject later from the Plan run page or the Migration tab (`approveStageRun`, `resolveApplicationMigrationRequest`).
- **Backend.** A stage whose `execution.mode` is `approve` makes the harness send an ACP `session/request_permission` for each tool call, over the run's WebSocket (`/hub/agentic/agentruns/:name/acp`, nonce from POST `/hub/agentic/agentruns/:name/acp/nonce`, scope `agentic.agentruns.acp:post`). The harness offers the ask only to viewers attached at that moment, and fails closed:
  - nobody attached: denied immediately;
  - attached but nobody answers within `HARNESS_HITL_TIMEOUT_SECONDS` (default 180, at most 600): denied, and later asks deny fast until a viewer attaches or answers again.

  Sources: agentic-controller `harness/README.md` ("Permission asks"), `harness/internal/acp/session.go` (`ForwardNoViewers`, `ForwardTimeout`), `harness/internal/tee/tee.go` (`ForwardPermission`). Agent questions (`elicitation/create`, `ask_user`) behave the same and are opt-in per run (`spec.execution.askUser`).

- **Consequence.** "Action required, approve later from the inventory" does not exist in today's backend: by the time someone opens the inventory the request was denied and the agent moved on. The REST signatures cannot carry what an answer needs either (the permission request id and the chosen option id).
- **Options.**
  1. Attended approval only: approvals are answered in a live session panel; the inventory shows that a run in approval mode needs someone watching, not a pending decision.
  2. Backend change: the harness parks asks durably (a status condition or a Hub record) and resumes when answered. Needs controller and harness design.
  3. Do not offer approval mode for unattended starts.
- **Reference.** Upstream `client/src/app/pages/agent-runs/components/ChatPanel.tsx` (`git show upstream/main:client/src/app/pages/agent-runs/components/ChatPanel.tsx`) is the live session panel: it mints the nonce, dials only while `ACPReady` is True, renders permission asks and questions inline, and answers them. It drives `client/src/app/api/agentic/acp.ts` (`AcpSession`), which this branch keeps with no consumers.

### B. Runs need inputs the UI does not collect

- **Model (Gateway).** The controller defaults a run's `spec.gateway` only when the Agent declares exactly one Gateway; with none or several, a run without `spec.gateway` fails validation (`internal/controller/agentrun_controller.go:517-536`). Every Agent the operator ships declares none (`config/defaults/agent_migration_*.yaml`), so every run of the shipped `java-ee-to-quarkus` workflow must name one. `AgentWorkflowRun.spec.gateway` feeds each stage.
- **Target branch.** The migration harness refuses to start without `TARGET_BRANCH` (`harness/internal/config/config.go:183-193`). The start-migration dialog collects one; the Agent test dialog does not.
- **Parameters.** Required Agent parameters and workflow parameters have no input anywhere.
- **What is in place.** `AgentTestRunRequest` has optional `modelId`, `targetBranch` and `params`; `StartApplicationMigrationsRequest` has optional `modelId` and `params`. The adapters write them as `spec.gateway`, env `TARGET_BRANCH` and `spec.params` (`toCreateRunInput`, `toWorkflowRunInputs`). No UI sets them, and the prototype API ignores them.
- **Reference.** Upstream solved the inputs in `client/src/app/pages/agent-runs/components/GatewayPicker.tsx` (`gatewayRequiredFor`, `defaultGatewayFor`: which Gateways to offer and when a choice is required) and `client/src/app/pages/agent-runs/components/ParamFields.tsx` (`ParamValueField`, `paramValueInvalidReason`), used by `pages/agent-runs/components/CreateRunModal.tsx`, `pages/workflow-runs/components/CreateWorkflowRunModal.tsx` and `pages/applications/agent-run-modal/BulkAgentRunModal.tsx` (all on `upstream/main`).
- **Decision.** Where a run's Model comes from (a picker per start, or the organization default Model as the default `spec.gateway`, which needs the missing stored default), and whether missing required parameters block a start.

### C. Names are immutable

- `metadata.name` cannot change and the Hub's PUT copies only `spec`. Agents, Models (Gateways), Plans (AgentWorkflows) and Skill collections have no display-name field, so their name is `metadata.name`; a Skill's name is `spec.displayName` and can change. The forms let users edit every name.
- **Adapter rule in place.** Create: `toNewResourceName(name)` (a slug; throws when nothing usable is left). Update: `assertNotRenamed(id, name)` accepts a name that maps to the same resource name ("Java EE to Quarkus" for `java-ee-to-quarkus`) and throws `RenameNotSupportedError` otherwise, so a rename never silently does nothing. Description fields have no CRD field either.
- **Decision.** (1) Make the name read-only when editing (smallest change); (2) add a display name and description to the CRDs (annotation or spec field; backend change); or (3) rename as create plus delete (breaks references: `workflowRef`, `agentRef`, `skillCardRef`, and run history).

### D. One workflow run per application

- The controller runs one AgentWorkflowRun per application (label `konveyor.io/application`, env `APP_ID`). The prototype groups several applications in one plan run: Plan run pages list `applications[]`, and an approve or reject decides for every application in the run (the confirmation names them all).
- Wired, `startApplicationMigrations` becomes one create per application (`api/rest/agentic-hub.ts` creates them in sequence; partial failure is undefined), and every plan run has exactly one application.
- **Decision.** Keep a multi-application "batch" as a UX concept (it needs a batch label on the runs and grouping in the list; no such label exists today), or make the plan run per application and drop the grouping. Either way the run-wide decision wording goes.

## 1. What is mocked and how

### Mock transport

- Every agentic call goes to `/hub/prototype/agentic/*`. No Hub serves these paths; they are a prototype contract.
- In development, [MSW](https://mswjs.io) answers them in the browser: `client/src/mocks/stub-new-work/agentic/`.
  - `handlers.ts`: HTTP translation only. 201 + entity on create, 204 on PUT and DELETE, `{ message }` with 400 / 404 / 409. The URL id wins over a body id.
  - `catalog.ts`: configuration resources (validation, duplicate names, in-use deletes, verification).
  - `execution.ts`: plan runs and the per-application migration view, derived from one run store. Runs progress on read (Pending 2 s, then 4 s per stage). The default execution policy is `interactive`: a started run stops at every stage with `requiresApproval` (status `AwaitingApproval`, application intervention `actionRequired`) until someone approves or rejects it; `PUT /execution-policy` with `unattended` lets new runs pass those gates.
  - Plan resolution (`resolvePlanFor`): an application's archetype + target profile resolve to the Plan whose `migrationPath.isDefault` covers that profile, otherwise the application is not configured. The application's target profile is fixture data (`portfolio.ts` `APPLICATION_TARGET_PROFILE_IDS`; the archetype's first profile otherwise). "Make default" (`PUT /archetypes/:id/target-profiles/:id/plan`) moves the default; the previous default keeps its migration path (its other profiles, or the same profile as a non-default Plan). Create/update return 409 for a second default Plan on a profile and 400 for a Plan without stages or a path without target profiles.
  - `db.ts`: in-memory state cloned from `fixtures.ts` and `portfolio.ts`. A hard reload resets it.
  - `prototype-state.ts`: reads `protoScenario` and `protoStage` from the URL. Only the mocks read these.
- The production Express server (`server/`) serves no agentic data. It proxies `/hub/*` (with WebSocket upgrade for `/hub/agentic/`) like upstream.
- `MOCK` is read when the dev server starts (`client/src/mocks/config.ts`, `common/src/mock-config.ts`). **MSW only runs in development bundles** (`client/src/index.tsx`, `process.env.NODE_ENV === "development"`): a production build has no mocks, so every agentic call goes to the network.

| Goal                                   | Command (repo root)                               | Result                                                                                                                                                        |
| -------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Full prototype                         | `MOCK=stub AUTH_REQUIRED=false npm run start:dev` | All stub groups, `AGENTIC_ENABLED=true`, persona/scenario switcher                                                                                            |
| Real Hub plus agentic mocks            | `MOCK=stub=agentic.pass npm run start:dev`        | Only the agentic API is faked; other `/hub` calls pass through. The mock's migration views cover only its own 12 portfolio applications.                      |
| Agentic mocks plus prototype Hub fakes | `MOCK=stub=agentic,prototype-support.pass`        | Also fakes identities, tags, tasks, settings, tickets, reviews, facts, generators, analysis profiles                                                          |
| Real Hub only                          | `MOCK=off npm run start:dev`                      | No MSW. `AGENTIC_ENABLED` defaults to `false`; with `AGENTIC_ENABLED=true` the agentic pages call `/hub/prototype/agentic/*` and get 404 until you wire them. |

### `AGENTIC_ENABLED`

- Upstream flag (`common/src/env-types.ts`). Explicit value wins; otherwise it is `"true"` exactly when `MOCK` stubs the `agentic` group (`server/src/serverConfig.js`, `client/config/rspack.dev.mts`).
- `isAgenticEnabled` (`client/src/app/Constants.ts`) gates the agentic routes (`Routes.tsx`), the sidebar group, Administration > Providers / Models, and the agentic parts of the inventory, application detail, archetype drawer and target profiles page. It is one switch for everything; there is no flag per capability (see checklist step 8).
- `AGENTIC_STEER_ENABLED` (upstream, default `"false"`, `isAgenticSteerEnabled`) has no consumer on this branch: upstream's `ChatPanel` was its only one.
- When wiring the real backend, keep the flag and drop the MOCK-derived branch of its default.

### Prototype shell and switcher

- `isPrototypeEnabled` (`Constants.ts`) = development bundle, `AUTH_REQUIRED=false`, `AGENTIC_ENABLED`, and `MOCK` stubs `agentic`.

## 2. Data layer architecture

```
pages/** (agentic pages, inventory, application detail, archetypes)
  └─ queries/agentic.ts          TanStack Query hooks, keys, invalidation, polling
       └─ api/rest/agentic.ts    axios functions; AGENTIC_ENDPOINTS holds every path
            └─ /hub/prototype/agentic/*   MSW today  →  /hub/agentic/* after wiring

agentic/types.ts        UI domain model (what pages render)
agentic/projection.ts   pure presentation helpers over domain types
agentic/adapters/       CRD <-> domain mappers for the real backend (not wired yet)
api/rest/agentic-hub.ts  Hub-backed versions of the REST functions (reference, not imported)

Real-backend reference kept from upstream (not used by the prototype pages):
api/agentic/contract.ts   CRD types and helpers (konveyor.io/v1alpha1)
api/agentic/acp.ts        ACP JSON-RPC session over WebSocket (transcript, approvals, questions)
api/rest/agent-runs.ts    axios client for /hub/agentic/*
queries/agentic-polling.ts  AGENTIC_QUERY_RETRY, pollUnlessErrored (used by queries/agentic.ts)
utils/agentic.ts          run/application label helpers, run eligibility, stage preflight, RBAC error detection
utils/skills.ts           SkillCard conditions, source kind, SKILL.md frontmatter parsing and validation
```

Rules that hold today:

- Pages call hooks only. One exception: `pages/agentic/useEntityBreadcrumbs.ts` calls the `get*ById` REST functions directly, but with `agenticKeys.detail(...)` and `agenticRetry`, so cache and invalidation are shared.
- `api/rest.ts` does not re-export agentic REST: names collide with `api/rest/agent-runs.ts`. Import from `@app/api/rest/agentic`.
- REST functions return data, never the `AxiosResponse`. Creates resolve to the entity; updates and deletes resolve to `void` (the Hub answers 204).
- Ids are opaque strings (`EntityId`). Requests carry id-only refs (`IdRef`); the server owns names. Hub entities (applications, archetypes, target profiles, identities) keep numeric `HubRef`s.
- Page code depends only on the hooks and `@app/agentic`, but six page tests (`agent-detail`, `model-form`, `skill-forms`, `plan-wizard`, `provider-form`, `migration-preflight-modal`) stub HTTP at `AGENTIC_ENDPOINTS` with domain-shaped JSON. Swapping a REST group breaks those tests until they mock the REST functions (or the hooks) instead.

Where things live in `client/src/app/queries/agentic.ts`:

| Concern      | Where                                                                                                                                                                                                                                                                                                |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Query keys   | `agenticKeys` (root `"agentic"`, then group, then `list`/`detail`)                                                                                                                                                                                                                                   |
| Invalidation | `MUTATION_EFFECTS` (which groups each write invalidates) + `invalidateAgentic()`; every mutation's `onSuccess` calls it                                                                                                                                                                              |
| Polling      | `refetchInterval` per hook, wrapped in `pollUnlessErrored`. Models and Providers poll every 3 s while any is `pending`. App migrations poll every 3 s and plan runs every 5 s while active, and every 30 s once every active one waits for a decision. Agent test runs poll every 5 s while running. |
| Retry        | `agenticRetry`: never retry a 4xx, retry a 5xx once                                                                                                                                                                                                                                                  |
| Id guards    | `isUsableId` disables detail queries for `""`, `"NaN"`, `"undefined"`, `"null"`                                                                                                                                                                                                                      |
| Not found    | detail hooks return `isNotFound` next to `fetchError`                                                                                                                                                                                                                                                |

### Real-backend REST sketch

`client/src/app/api/rest/agentic-hub.ts` reimplements the groups the Hub serves (Skills, Skill collections, Models except create, Agents except create, Agent test runs, Plans, Plan runs, single-Plan starts) over `api/rest/agent-runs.ts` and the adapters. Each function has the name and signature of its `api/rest/agentic.ts` counterpart, which `agentic-hub.test.ts` enforces at compile time, so wiring a group is moving its functions over. App code does not import it. Its header lists what it leaves out (blocked creates, ACP, missing groups) and the open limits (application names, whole-namespace polling, last write wins). It writes agent-scope Skill associations to the Agents (one PUT per changed Agent, not atomic) and refuses Hub-scope associations and renames instead of dropping them.

Hub response semantics (`internal/api/agentic.go`, `internal/api/base.go`, `internal/api/error.go`):

- List returns a bare JSON array, no pagination, no filters. Create returns **201** with the object. PUT returns **204** and copies **only `spec`** onto the stored object (`current.Spec = r.Spec`; labels, annotations and the name cannot change). DELETE returns **204**, also for a missing object: the handler's Get fails with NotFound, and the error handler answers NotFound on a DELETE with 204 (`error.go:144-152`).
- **Strict request bodies.** `BindJSON` calls `DisallowUnknownFields` (`base.go:216-230`), and the bodies decode into the controller's own Go types at the version the Hub pins (`go.mod:19`, `agentic-controller/api` @ `38046470`). Any field that version does not know is a **400**. That pin, not controller `main`, is what `contract.ts` and the adapters must match; the fields listed under [Contract drift](#contract-drift) are all present at the pin.
- Workflow runs and agent runs have no PUT. On create the Hub mints a token Secret, adds it as `envFrom`, and appends `HUB_BASE_URL` to `spec.env`. The client sends `APP_ID` and `TARGET_BRANCH` in `spec.env` and the `konveyor.io/application` label (`createAgentRun` / `createWorkflowRun` do this).
- Errors: a k8s NotFound becomes 404 (204 on DELETE) and a body bind error becomes 400. Other k8s errors (AlreadyExists, Invalid from CRD validation, Forbidden for the Hub's ServiceAccount) fall through to **500** with the k8s message. `utils/agentic.ts` `isAgenticRbacError` detects the RBAC case.
- The Hub does not check references: deleting an Agent used by a workflow, or a SkillCard used by an Agent, succeeds.

## 4. Entity and field mapping

General rules:

- `id` ↔ `metadata.name` (DNS-1123: `^[a-z0-9]([a-z0-9.-]*[a-z0-9])?$`). The name is chosen by the client on create and cannot change. Runs use `generateName: "ui-"`.
- `name` (display) ↔ `metadata.name`, except SkillCard (`spec.displayName`). `toResourceName()` slugs display text into a resource name.
- `EntityRef` ↔ a bare name: `{ ref }`, `agentRef`, `workflowRef`, `skillCardRef`. The adapters build refs whose `name` is the id unless you pass a `NameIndex` (`toNameIndex(domainEntities)`).
- `createTime` ↔ `metadata.creationTimestamp`. `updateTime` has no source.
- Updates: the Hub replaces the whole `spec`, so every `to*Spec` writer takes the current spec as `base` and spreads it (stage and parameter entries too), so CRD fields the domain does not model, including fields a newer controller adds, survive a save. `real-samples.test.ts` round-trips every controller default and sample CR (fixtures: `agentic/adapters/__fixtures__/agentic-controller-369070c6/`, verbatim from that commit).
- Names: create with `toNewResourceName(name)`; before an update call `assertNotRenamed(id, name)` (see [C](#c-names-are-immutable)).
- Operator-owned objects: `Agent`, `Skill`, `SkillCollection` and `MigrationPlan` have an optional `operatorManaged` (label `app.kubernetes.io/managed-by: agentic-controller-defaults`, `utils/agentic.ts` `isOperatorManaged`). The operator reverts edits to these, so pages should render them read-only. The adapters set it; the prototype API never does, and no page reads it yet.
- "no source" below means the adapter returns the stated default and the gap is listed in section 7.

## 7. Known gaps and open backend questions

### Backend contract missing

1. **Application migration aggregate** (`GET /application-migrations`): resolved Plan, preflight, latest run, intervention, effective skills, results, for every application. Prefer a POST body or server-side filter over the `applicationIds` query string.
2. **Plan resolution and migration paths**: archetype + target profiles → Plan (`assignPlanToTargetProfile`, `MigrationPlan.migrationPath`, "Use recommended Plan").
3. **Preflight** (`preflight`, `preflightReason`) and duplicate-run protection.
4. **Provider** resource and **available models** per provider.
5. **Organization default Model** (`isOrganizationDefault`, `setDefaultModel`).
6. **Execution policy** (org-wide unattended / interactive). The controller only has per-stage / per-run `execution.mode`.
7. **Hub-scope Skill associations** (archetype, target profile, application) and effective-skill provenance.
8. **Run results** (`ApplicationMigrationResult`, stage `commits`). Part of this is in ACP plan-entry `_meta` (`konveyor.io/plan`, see `acp.ts` `PlanRungMeta`).
9. **Descriptions and display names** for Agent, Gateway, AgentWorkflow and SkillCollection (no CRD field; the forms have free-text names such as "Java EE to Quarkus"). Options: slug names (`toResourceName`) plus a display-name annotation, or new spec fields.
10. **Rename**: `metadata.name` is immutable and the Hub copies only `spec` on PUT, so editing a name is impossible except a SkillCard's `displayName`. The forms allow renaming; the adapters refuse it (`assertNotRenamed`). See [C](#c-names-are-immutable).

### Semantics that differ

11. **Approval granularity and timing**: the prototype approves a stage, at any later time; the backend approves tool calls (ACP `session/request_permission`) inside a stage whose `execution.mode` is `approve`, only while someone is attached, and denies otherwise. `ControllerRunPhase` still contains `AwaitingApproval`; a pending approval should be `intervention`, separate from phase. See [A](#a-approvals-happen-inside-a-live-session-and-are-denied-when-nobody-is-watching).
12. **One run per application**: the prototype groups several applications in one plan run; the controller runs one AgentWorkflowRun per application. Plan run list and detail pages show `applications[]`. Known gap: because the prototype's run is shared, an approve or reject from one application's Migration tab (`POST /application-migrations/:appId/requests/current`) decides for every application in that run. The UI says so and names every affected application in a confirmation; with the backend's per-application runs the decision becomes per application and that wording can go. See [D](#d-one-workflow-run-per-application).
13. **Reject**: no reject endpoint; deny the ACP permission or delete the run.
14. **Required CRD fields the UI cannot supply**: `Agent.spec.image`; `Gateway.spec.credentialRef` (a k8s Secret, while the form picks a Hub identity) and `spec.model.contextWindow`; a run's `spec.gateway`, `TARGET_BRANCH` for test runs and required parameters ([B](#b-runs-need-inputs-the-ui-does-not-collect)). The forms need these fields, or the Hub needs defaults. The UI has no API to create the credential Secret.
15. **Referential integrity**: the Hub deletes referenced resources without a 409, and returns 500 for AlreadyExists and CRD validation errors. Duplicate-name and in-use messages the mock gives as 409 will arrive as 500 with a k8s message; nothing maps those messages to form errors yet.
16. **Managed-label filter**: `GET /agentic/agents` and `/agentic/workflows` list only `konveyor.io/managed=true` (the Hub adds it on create; the shipped defaults carry it). Objects the operator owns (`app.kubernetes.io/managed-by=agentic-controller-defaults`) revert edits; the adapters expose this as `operatorManaged`, but no page renders those objects read-only yet (`utils/agentic.ts` `operatorManagedActionProps` disables a row action with a tooltip).
17. **Gateway "verified" vs usable**: `VerificationSkipped` makes a Gateway Ready but unverified; `VerificationStatus` has no value for that (the adapter maps it to `verified` with the message in `statusReason`).
18. **Model form depends on Providers**: the Model form picks its provider from `useFetchProviders` (missing backend) and its model from `useFetchAvailableModels` (missing). Wiring Models alone still needs a decision on Provider (section 4).
19. **Conditions not in the domain**: Agent Ready / `GatewayConfigured`, AgentWorkflow Ready (`AllAgentsReady`), SkillCard `type` and `Resolvable`, Gateway `contextWindow` and `tier`. Add them to the domain types when a page needs them.

### Prototype data-layer items (not fixed here)

20. Hooks and types still say Gateway (`useFetchGateways`, `Gateway`) while the REST functions and UI say Model.
21. Execution policy: `getExecutionPolicy` / `updateExecutionPolicy`, the `executionPolicy` query group and its `MUTATION_EFFECTS` entry remain for the mock (whose default is `interactive`), but no hook or page uses them.
22. `useFetchAgentTestRuns` assumes a server-side `agentId` filter, and `useFetchPlanRuns` a `planId` filter. With the real API, filter client-side and exclude stage AgentRuns (`isAgentTestRun`), as `agentic-hub.ts` does.
23. The mock serves migration views only for its 12 portfolio applications, and resolves applications from mock data even with `MOCK=stub=agentic.pass`.
24. Run application names: the adapters name a run's application `#<id>` unless given an `ApplicationNameIndex`; join `useFetchApplications` in the hook. A test run with no application maps to `{ id: 0, name: "" }`, and a run with no timestamps to `startedAt: ""`.

## 8. Wiring checklist

Do these in order; each step leaves the app working.

1. **Reach the Hub.** You need a cluster with Agent Sandbox, an agentic-enabled Hub, the agentic controller and its defaults, a credential Secret and at least one Gateway: follow agentic-controller `docs/getting-started.md` sections 1 to 4 (`docs/local-minikube-setup.md` in this repo does not cover agentic). Then run `MOCK=stub=agentic.pass AUTH_REQUIRED=true npm run start:dev` (it already runs `npm run port-forward`; do not start a second one). Confirm `GET /hub/agentic/agents` works with your token and that the WebSocket upgrade for `/hub/agentic/` passes the proxy (`server/src/index.js`).
2. **Refresh the contract.** Update `api/agentic/contract.ts` to the controller API the Hub pins (`go.mod`; `38046470` today, see [Contract drift](#contract-drift)). Re-copy the controller's `config/defaults` and `config/samples` into `agentic/adapters/__fixtures__/` from the same version and rerun `real-samples.test.ts`.
3. **Decide the open questions.** [Design questions A to D](#design-questions-blocking-backend-integration), and section 7 items 9, 14 and 18: display names and descriptions, rename, where `image`, `credentialRef` and `contextWindow` come from, how a credential Secret gets created (the UI has no API for it), the run Model, and Provider. Add the form fields or Hub defaults.
4. **Swap the catalog reads.** Move the read functions from `api/rest/agentic-hub.ts` into `api/rest/agentic.ts` (`getSkills`, `getSkillById`, `getSkillCollections`, `getSkillCollectionById`, `getModels`, `getModelById`, `getAgents`, `getAgentById`, `getMigrationPlans`, `getMigrationPlanById`). They make extra fetches for joins: Skills fetch the Agents, Agents and collections fetch every SkillCard for names, Plans fetch every workflow run for `runCount`. Decide whether joins stay in the REST function or move into hooks (shared cache, fewer refetches while polling). Update the page tests that stub `AGENTIC_ENDPOINTS` (section 2).
5. **Swap the catalog writes.** Move the create/update/delete functions over. Each update calls `assertNotRenamed`, fetches the current object, then writes `to*Spec(request, current.spec)`. Add a helper that maps the Hub's 500 messages (AlreadyExists, Invalid, Forbidden; `isAgenticRbacError`) to form errors. `createModel` and `createAgent` wait for step 3. Render `operatorManaged` objects read-only.
6. **Swap runs.** Move `getPlanRuns`, `getPlanRunById`, `getAgentTestRuns`, `startAgentTestRun` and `startApplicationMigrations` over (single-Plan only until resolution exists). Collect the run Model, target branch and parameters first ([B](#b-runs-need-inputs-the-ui-does-not-collect)); runs of the shipped workflow fail without a Model. Settle partial failure of multi-application starts and the run grouping ([D](#d-one-workflow-run-per-application)). Join application names in the hooks.
7. **Approvals over ACP.** Only after [A](#a-approvals-happen-inside-a-live-session-and-are-denied-when-nobody-is-watching) is decided. Port a session hook from upstream `ChatPanel.tsx` over `api/agentic/acp.ts` (`mintAcpNonce`, `getAgenticAcpUrl`); dial only while the AgentRun's `ACPReady` condition is True; gate on `agenticAcpScopes`. The approval mutations then take the AgentRun name, the permission request id and the option id; `AwaitingApproval` goes.
8. **Gate what the backend does not serve.** MSW is not in production bundles, so a production build with `AGENTIC_ENABLED=true` sends every call for a missing group to `/hub/prototype/agentic/*`, which no Hub serves. The affected surfaces:
   - application migrations: the inventory migration column, next action and Start (`applications-table.tsx`), the Migration tab (`migration-tab.tsx`), the start dialog (`migration-preflight-modal.tsx`, `use-start-migrations.ts`);
   - Providers and available models: Administration > Providers (`providers.tsx`, `provider-form.tsx`) and the Model form (`model-form.tsx`);
   - the organization default Model (`models.tsx`, "make default");
   - Plan migration paths: Assign/Change Plan on `target-profiles-page.tsx`, the wizard's path step (`plan-wizard.tsx`), path columns and details in `plans.tsx`, `plan-details.tsx`, the Skill form's archetype and profile scopes;
   - approvals (`plan-run-detail.tsx`, `stage-run-detail.tsx`, `migration-tab.tsx`) until step 7.

   Options:
   - **(a) Do not enable in production until everything is wired.** Keep `AGENTIC_ENABLED` off in production builds. Simple and safe, but nothing ships until the last missing group has a backend.
   - **(b) A capability map in code.** One module (for example `agentic/capabilities.ts`) exports which groups the backend serves; routes, sidebar entries, table columns and actions check it next to `isAgenticEnabled`. Flip an entry when its backend ships in the Hub version the UI is released with.
   - **(c) Per-capability environment flags.** Like (b), but each entry comes from `window._env` (`AGENTIC_<GROUP>_ENABLED`). Only worth it if one UI build must run against Hubs with different agentic API levels.
   - **(d) Runtime detection.** Probe each group (404 or 405 means missing) and hide it. Adds a request and a loading state per surface, and turns a misconfigured proxy into a silently hidden feature.

   **Recommended: (b).** The operator installs the UI with a matching Hub, so what the backend serves is a property of the release, not of a deployment; a typed map keeps the gating explicit, testable and greppable, with no new configuration surface. Move the missing groups' paths into their own `AGENTIC_ENDPOINTS` group so the split is visible. Until a group is gated, it must stay unwired and its surfaces hidden: never rely on the mock in a build that can reach production.

9. **Mocks in CRD shape (recommended).** Make MSW serve CRD objects at `/hub/agentic/*` for the swapped groups (reuse the fixtures through reverse mappers), so local development and the e2e suite run the same adapters as production. Without it, every swapped group loses its mock.
10. **Clean up.** Strip the prototype shell (section 1), remove `AwaitingApproval` from `ControllerRunPhase`, rename the Gateway hooks and types to Model, keep one set of agentic scope constants, and move configuration checks to conditions (section 5).
11. **Verify.** `npm test -w client` (adapters: `client/src/app/agentic/adapters/{adapters,real-samples}.test.ts`; Hub module: `client/src/app/api/rest/agentic-hub.test.ts`). The Playwright suite in `e2e/` is prototype-only (it drives the mock through `protoScenario` / `protoPersona`); against a real cluster, test by hand or write new specs, including Hub errors (RBAC 500, missing objects, operator-managed objects, runs without a Model, denied approvals).
