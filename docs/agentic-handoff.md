## Design questions blocking backend integration

Read this first. These four are product, UX or backend decisions, not wiring tasks. Each blocks part of the [wiring checklist](#8-wiring-checklist), and none can be solved in the REST layer alone.

### A. Approvals happen inside a live session, and are denied when nobody is watching

- **Prototype model.** A started run reaches `AwaitingApproval`; the application shows `actionRequired` as its inventory status; anyone can approve or reject later from the Plan run page or the Migration tab (`approveStageRun`, `resolveApplicationMigrationRequest`).
- **Backend.** A stage whose `execution.mode` is `approve` makes the harness send an ACP `session/request_permission` for each tool call, over the run's WebSocket (`/hub/agentic/agentruns/:name/acp`, nonce from POST `/hub/agentic/agentruns/:name/acp/nonce`, scope `agentic.agentruns.acp:post`). The harness offers the ask only to viewers attached at that moment, and fails closed:
  - nobody attached: denied immediately;
  - attached but nobody answers within `HARNESS_HITL_TIMEOUT_SECONDS` (default 180, at most 600): denied, and later asks deny fast until a viewer attaches or answers again.

  Sources: agentic-controller `harness/README.md` ("Permission asks"), `harness/internal/acp/session.go` (`ForwardNoViewers`, `ForwardTimeout`), `harness/internal/tee/tee.go` (`ForwardPermission`). Agent questions (`elicitation/create`, `ask_user`) behave the same and are opt-in per run (`spec.execution.askUser`).

- **Consequence.** "Action required, approve later from the inventory" does not exist in today's backend: by the time someone opens the inventory the request was denied and the agent moved on. The REST signatures cannot carry what an answer needs either (the permission request id and the chosen option id).
- **Options.**
  1. Attended approval only: approvals are answered in a live session panel; the inventory shows that a run in approval mode needs someone watching, not a pending decision.
  2. Backend change: the harness parks asks durably (a status condition or a Hub record) and resumes when answered. Needs controller and harness design.
  3. Do not offer approval mode for unattended starts.
- **Reference.** Upstream `client/src/app/pages/agent-runs/components/ChatPanel.tsx` (`git show upstream/main:client/src/app/pages/agent-runs/components/ChatPanel.tsx`) is the live session panel: it mints the nonce, dials only while `ACPReady` is True, renders permission asks and questions inline, and answers them. It drives `client/src/app/api/agentic/acp.ts` (`AcpSession`), which this branch keeps with no consumers.

### B. Runs need inputs the UI does not collect

- **Model (Gateway).** The controller defaults a run's `spec.gateway` only when the Agent declares exactly one Gateway; with none or several, a run without `spec.gateway` fails validation (`internal/controller/agentrun_controller.go:517-536`). Every Agent the operator ships declares none (`config/defaults/agent_migration_*.yaml`), so every run of the shipped `java-ee-to-quarkus` workflow must name one. `AgentWorkflowRun.spec.gateway` feeds each stage.
- **Target branch.** The migration harness refuses to start without `TARGET_BRANCH` (`harness/internal/config/config.go:183-193`). The start-migration dialog collects one; the Agent test dialog does not.
- **Parameters.** Required Agent parameters and workflow parameters have no input anywhere.
- **What is in place.** `AgentTestRunRequest` has optional `modelId`, `targetBranch` and `params`; `StartApplicationMigrationsRequest` has optional `modelId` and `params`. The adapters write them as `spec.gateway`, env `TARGET_BRANCH` and `spec.params` (`toCreateRunInput`, `toWorkflowRunInputs`). No UI sets them, and the prototype API ignores them.
- **Reference.** Upstream solved the inputs in `client/src/app/pages/agent-runs/components/GatewayPicker.tsx` (`gatewayRequiredFor`, `defaultGatewayFor`: which Gateways to offer and when a choice is required) and `client/src/app/pages/agent-runs/components/ParamFields.tsx` (`ParamValueField`, `paramValueInvalidReason`), used by `pages/agent-runs/components/CreateRunModal.tsx`, `pages/workflow-runs/components/CreateWorkflowRunModal.tsx` and `pages/applications/agent-run-modal/BulkAgentRunModal.tsx` (all on `upstream/main`).
- **Decision.** Where a run's Model comes from (a picker per start, or the organization default Model as the default `spec.gateway`, which needs the missing stored default), and whether missing required parameters block a start.

### C. Names are immutable

- `metadata.name` cannot change and the Hub's PUT copies only `spec`. Agents, Models (Gateways), Plans (AgentWorkflows) and Skill collections have no display-name field, so their name is `metadata.name`; a Skill's name is `spec.displayName` and can change. The forms let users edit every name.
- **Adapter rule in place.** Create: `toNewResourceName(name)` (a slug; throws when nothing usable is left). Update: `assertNotRenamed(id, name)` accepts a name that maps to the same resource name ("Java EE to Quarkus" for `java-ee-to-quarkus`) and throws `RenameNotSupportedError` otherwise, so a rename never silently does nothing. Description fields have no CRD field either.
- **Decision.** (1) Make the name read-only when editing (smallest change); (2) add a display name and description to the CRDs (annotation or spec field; backend change); or (3) rename as create plus delete (breaks references: `workflowRef`, `agentRef`, `skillCardRef`, and run history).

### D. One workflow run per application

- The controller runs one AgentWorkflowRun per application (label `konveyor.io/application`, env `APP_ID`). The prototype groups several applications in one plan run: Plan run pages list `applications[]`, and an approve or reject decides for every application in the run (the confirmation names them all).
- Wired, `startApplicationMigrations` becomes one create per application (`api/rest/agentic-hub.ts` creates them in sequence; partial failure is undefined), and every plan run has exactly one application.
- **Decision.** Keep a multi-application "batch" as a UX concept (it needs a batch label on the runs and grouping in the list; no such label exists today), or make the plan run per application and drop the grouping. Either way the run-wide decision wording goes.

## 1. What is mocked and how

### Mock transport

- Every agentic call goes to `/hub/prototype/agentic/*`. No Hub serves these paths; they are a prototype contract.
- In development, [MSW](https://mswjs.io) answers them in the browser: `client/src/mocks/stub-new-work/agentic/`.
  - `handlers.ts`: HTTP translation only. 201 + entity on create, 204 on PUT and DELETE, `{ message }` with 400 / 404 / 409. The URL id wins over a body id.
  - `catalog.ts`: configuration resources (validation, duplicate names, in-use deletes, verification).
  - `execution.ts`: plan runs and the per-application migration view, derived from one run store. Runs progress on read (Pending 2 s, then 4 s per stage). The default execution policy is `interactive`: a started run stops at every stage with `requiresApproval` (status `AwaitingApproval`, application intervention `actionRequired`) until someone approves or rejects it; `PUT /execution-policy` with `unattended` lets new runs pass those gates.
  - `observability.ts`: the AgentRun behind every started stage, one per application of the run (run observability; see [Multi-application run observability](#multi-application-run-observability)), with no state of its own (it reads the run store like every other read, which advances runs on read): `StageAgentRun` summaries, the AgentRun CR, the folded transcript and per-container logs, all generated from one deterministic script per stage (ACP frames and harness log lines over 2.5 minutes) and folded by the real `foldTranscript` adapter, so transcript, usage and logs agree. A Running stage reveals the script by the clock its progress messages use (`execution.ts` `getStageLiveSince`): a step about every 5 s, log lines about every second, then a plateau. Finished and awaiting stages return everything, spread over their real duration; one shorter than the script (the 4 s stages of a run started in the prototype) returns what it reached at real time and then its closing frames and lines at its end, so the log stays append-only across the stage's end, as on the hub. A stage awaiting approval has finished its turn, so its transcript is `complete` while its pod, and so its log, stays `live`; approve mode stages stay `skipped`. The `actionRequired` scenario can gate a stage whose plan does not require approval (for example `protoStage=2`), so that stage page shows "Approval: Not required" next to the approval alert and a recorded transcript; on the backend such a stage would run in approve mode and not be recorded. A recorded stage's messages are in its transcript too; an approve mode stage has none, so its Transcript tab shows `StageRun.messages` (the live ACP session, wiring step 7) under the not-recorded sentence. A stage's output is the CR's `terminationData.stopReason`. Demo states: context climbs through 80 % and compacts once on metered stages; stage `3` compacts twice and ends at 95 %+; stages on the self-hosted Llama Model report no context; finished stage `2` has a 24,000+ line agent log (generated once, cached) and an `incomplete` transcript with a gap; approve mode stages are `skipped`. Log offsets count UTF-8 bytes like the hub's (an offset inside a character starts at the next one, since JSON carries characters), an offset at or past the end answers an empty chunk (200) and only a malformed offset a 400, and the logs use only high-contrast ANSI colors. The mock never answers 404 for a started stage; the hub does for its first seconds (see the `AgentRunLogChunk` notes), which the hook tests cover.
  - Plan resolution (`resolvePlanFor`): an application's target profile is its archetype's target profile (one per archetype; when an archetype has several, the first; with several archetypes, the first one that has a profile: `targetProfileFor` in `skill-resolution.ts`). Its plan is the Plan whose `migrationPath.isDefault` covers that archetype and profile, otherwise the application is not configured. It never follows the application's last run: the migration view's `plan` is the plan the next run uses, `planRunPlan` the plan its latest run used, and "Use each application's migration plan" starts each application on its own `plan`. Plan impact (`applicationImpact.matching`) counts applications by that plan. "Make default" (`PUT /archetypes/:id/target-profiles/:id/plan`) moves the default; the previous default keeps its migration path (its other profiles, or the same profile as a non-default Plan). Create/update return 409 for a second default Plan on a profile and 400 for a Plan without stages or a path without target profiles.
  - Skill resolution (`resolveSkillsByStage` in `skill-resolution.ts`, the only resolver): see [Skill resolution](#skill-resolution) below. `POST /plans/skills/resolve`, `GET /skills/:id/plans`, the application view, run creation and the seeded runs all read it. Ids that reference nothing add nothing (400 only for a malformed body); `apiError` and `loading` apply as for reads. `GET /skills/:id/plans` (`listSkillPlans` in `catalog.ts`) returns the saved plans whose preview lists the skill, with its `placements` (per stage, and one without `stage` for every stage), in plan name order; 404 for an unknown skill, and the scenarios apply as for reads (`initial` hides fixture skills and plans). The resolve preview hides nothing in `initial`, like a saved plan's resolution (7.7).
  - "Assigned" in the UI means exactly that default plan. Archetype surfaces (target profiles page, archetype drawer Target profiles tab, Archetypes list) show only the assigned plan of each profile, through one hook (`pages/archetypes/hooks/useTargetProfilePlans.ts`); plan surfaces list every target profile in the path and say when the plan is not assigned. "Assign migration plan" writes that default through `assignPlanToTargetProfile`.
  - `db.ts`: in-memory state cloned from `fixtures.ts` and `portfolio.ts`. A hard reload resets it.
  - `prototype-state.ts`: reads `protoScenario` and `protoStage` from the URL. Only the mocks read these.
- The production Express server (`server/`) serves no agentic data. It proxies `/hub/*` (with WebSocket upgrade for `/hub/agentic/`) like upstream.
- `MOCK` is read when the dev server starts (`client/src/mocks/config.ts`, `common/src/mock-config.ts`). **MSW only runs in development bundles** (`client/src/index.tsx`, `process.env.NODE_ENV === "development"`): a production build has no mocks, so every agentic call goes to the network.

### Skill resolution

Two concepts: a skill is **attached** to one thing (an agent and the skill collections it uses, an archetype, a target profile, an application), and **what each stage gets** follows from the attachments plus the plan's exclusions. The mock computes the second in one place, `resolveSkillsByStage` in `client/src/mocks/stub-new-work/agentic/skill-resolution.ts`, keyed by stage. Its readers: `POST /plans/skills/resolve` (with and without `applications`), `GET /skills/:id/plans`, the application migration view, `createRun` and the seeded runs (snapshots computed when the world is seeded).

Rules:

1. A stage gets its agent's own skills and the skills of the collections that agent uses, and nothing from other stages (the controller loads skills per AgentRun the same way, `resolveSkillVolumes`).
2. Context skills reach every stage and are listed once, in an `everyStage` group. For an application: the skills attached to each of its archetypes (all of them, merged), to its own target profile (its archetype's; the first when there are several) and to the application. For a plan preview without applications: the plan's archetype and the target profiles of its migration path, in one group without `application`.
3. A plan exclusion applies to every origin except the application itself: a skill with an application origin is never excluded. Excluded skills stay listed with `excluded: true`. In a stage group the exclusion always applies (stage groups have no application origin); the same skill in the application's every-stage group is not excluded, so it still reaches every stage.
4. Origins are deduplicated and ordered agent, collection, archetype, target profile, application; skills follow their first origin. Unknown agents, collections, archetypes, target profiles, applications and skills add nothing (a stage whose agent is unknown is listed with no skills).
5. A run on several applications stays one run, with one `everyStage` group per application: one application's context never reaches another.
6. A run can pick another target profile per application, or none, and exclude skills of its own, for every origin: see [Run skill review](#run-skill-review-target-profile-pick-and-run-exclusions).

Shapes (`client/src/app/agentic/types.ts`):

| Field                             | Meaning                                                                                                                                                   |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SkillsByStage`                   | `{ stages: StageSkillsGroup[]; everyStage: EveryStageSkillsGroup[] }`                                                                                     |
| `StageSkillsGroup`                | `order` (1-based), `name` (stage name), `agent`, `stageId` (run snapshots), `skills`                                                                      |
| `EveryStageSkillsGroup`           | `application?` (absent in a plan preview), `skills`                                                                                                       |
| `StageSkill`                      | `skill`, `loadPolicy`, `from: SkillOrigin[]`, `excluded`                                                                                                  |
| `SkillOrigin`                     | `agent`, `collection` (agent and collection), `archetype`, `targetProfile` (profile and its archetype), `application`; refs only, the UI writes the words |
| `ResolvePlanSkillsRequest`        | `stages: { agent, name? }[]`, `migrationPath?`, `excludedSkills?`, `applications?`                                                                        |
| `ResolvePlanSkillsResponse`       | `SkillsByStage`                                                                                                                                           |

Backend needs:

- Hub storage for archetype, target profile and application skill attachments (a join table), which Manage skills writes (UX first: Manage skills stays).
- One optional run-level skills field the Hub fills when it creates a run, merged by `resolveSkillVolumes` after the agent's own skills. Agent test runs fill it with their added skills ([Agent test run ↔ AgentRun](#agent-test-run--agentrun-agenticagentruns)).
- Recording what each stage got (agentic-controller#172), so a run shows its real snapshot.
- A per-stage preview endpoint (`POST /hub/agentic/workflows/skills/resolve`, see 7.7) answering `SkillsByStage`.
- Plan exclusions stored per stage (`AgentWorkflowStage.skills.exclude[]`, see 7.7).
- `SkillCard.spec.type` mapped to `loadPolicy` (done in the adapter: `rule` / `skill`).

### Multi-application run observability

A prototype data change that changes existing mock data (its own commit). Before it, a plan run on several applications had one agent run per stage, labelled with the run's first application only, and its skill loader staged that application's every-stage skills for everyone. The real backend runs one AgentWorkflowRun per application, so a stage has one AgentRun per application. The observability mock (`observability.ts`) now matches:

- One agent run per started stage per application, listed by `GET /plan-runs/:id/agent-runs` in stage order, then the run's application order. Each has its application (`StageAgentRun.application`, from the `konveyor.io/application` label, else `APP_ID`, named through `applicationNames`, else `#{id}`), its own name, its own skill loader list (the stage's group of the run's skills snapshot plus that application's every-stage group, minus excluded rows: an application's own skills never reach another application's agent run), its own transcript text (it clones its application's repository, says which application it works on, and names it where the stage's instructions say "the application") and its own context curve (growth varied by up to 10 % per application, deterministic by name).
- Names: the first application keeps the stage's name (`run-{run}-{stage}`); the others add `-app-{application id}` (the stage slug is cut, never a suffix, and a name that still collides gets `-{stage}-{application}`); their `konveyor.io/agentworkflowrun` label is `run-{run}-app-{application id}`, the first application's stays `run-{run}`. So a run on one application is unchanged, and a consumer that takes a stage's first agent run (today's stage page and Stages table) reads the first application's, as before.
- Phase rule: an agent run follows its stage, except that a Failed or AwaitingApproval stage fails or waits for the run's first application only. The other applications' agent runs for that stage Succeeded (in a Failed stage at the stage's end, in an AwaitingApproval stage when the proposal was ready; pinned to the stage's last message up to the decision, so approving or rejecting later never moves it). The `StageRun.status` stays the run-level aggregate (the worst state shows), so there is one failure and one decision per stage, which is what the stage's single Approve action and the plan run's attention alert assume. Running, Succeeded and Pending stages are the same for every application. The stage's messages (the plan run's activity, including a failure output or a proposal) and its output are the first application's agent run's; the other agent runs end with `end_turn`. Scenarios without runs (`initial`, `partialConfiguration`), `apiError` and `loading` are unchanged.
- Data layer for the stage page: `stageAgentRunsOf(agentRuns, stageId)`, `stageAgentRunFor(stageAgentRuns, applicationId)` and `defaultStageAgentRun(stageAgentRuns, applications)` (Action required, then Failed, then the run's application order) in `agentic/observability.ts`; `useFetchStageAgentRuns(runId, stageId, runPhase)` (the plan run list query, filtered: one cache entry and one poll per plan run). The selected agent run's resource, transcript and logs use the existing name-based hooks, with that agent run's `phase`, not the stage's (in a run on several applications the stage shows the worst state, so another application's finished agent run would keep polling). No new endpoint: the plan run list already answers every application's agent runs.
- Commits per application (a second change to existing mock data, its own commit): `ApplicationMigrationCommit.application?: HubRef` names the application whose agent run made the commit. In a run on several applications each seeded commit of a stage is one commit per application (the first application keeps the seeded hash, the others get their own), so `StageRun.commits` lists every application's commits and the stage page shows the selected application's (`isCommitOf`). An application's Migration tab result and its agent run's "Pushed ... commits" line count only its own. A run on one application has commits without `application`, as before. Real backend: commits are per AgentRun (each application's AgentWorkflowRun pushes to that application's repository); the Hub needs to report them per agent run or per repository.

## 2. Data layer architecture

```

  └─ queries/agentic.ts          TanStack Query hooks, keys, invalidation, polling

agentic/projection.ts   pure presentation helpers over domain types

Real-backend reference kept from upstream (not used by the prototype pages):
```

Rules that hold today:

- Pages call hooks only. One exception: `pages/agentic/useEntityBreadcrumbs.ts` calls the `get*ById` REST functions directly, but with `agenticKeys.detail(...)` and `agenticRetry`, so cache and invalidation are shared.
- `api/rest.ts` does not re-export agentic REST: names collide with `api/rest/agent-runs.ts`. Import from `@app/api/rest/agentic`.
- REST functions return data, never the `AxiosResponse`. Creates resolve to the entity; updates and deletes resolve to `void` (the Hub answers 204).
- Ids are opaque strings (`EntityId`). Requests carry id-only refs (`IdRef`); the server owns names. Hub entities (applications, archetypes, target profiles, identities) keep numeric `HubRef`s.
- Page code depends only on the hooks and `@app/agentic`, but six page tests (`agent-detail`, `model-form`, `skill-forms`, `plan-wizard`, `provider-form`, `migration-preflight-modal`) stub HTTP at `AGENTIC_ENDPOINTS` with domain-shaped JSON. Swapping a REST group breaks those tests until they mock the REST functions (or the hooks) instead.

Where things live in `client/src/app/queries/agentic.ts`:

| Concern      | Where                                                                                                                                                                                                                                                                                                |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Query keys   | `agenticKeys` (root `"agentic"`, then group, then `list`/`detail`)                                                                                                                                                                                                                                   |
| Invalidation | `MUTATION_EFFECTS` (which groups each write invalidates) + `invalidateAgentic()`; every mutation's `onSuccess` calls it                                                                                                                                                                              |

| Retry        | `agenticRetry`: never retry a 4xx, retry a 5xx once                                                                                                                                                                                                                                                  |

| Not found    | detail hooks return `isNotFound` next to `fetchError`                                                                                                                                                                                                                                                |

### Real-backend REST sketch

`client/src/app/api/rest/agentic-hub.ts` reimplements the groups the Hub serves (Skills, Skill collections, Models except create, Agents except create, Agent test runs, Plans, Plan runs, single-Plan starts) over `api/rest/agent-runs.ts` and the adapters. App code does not import it. Its header lists what it leaves out (blocked creates, ACP, missing groups) and the open limits (application names, whole-namespace polling, last write wins). It writes agent-scope Skill attachments to the Agents (one PUT per changed Agent, not atomic) and refuses Hub-scope associations and renames instead of dropping them.

Hub response semantics (`internal/api/agentic.go`, `internal/api/base.go`, `internal/api/error.go`):

- List returns a bare JSON array, no pagination, no filters. Create returns **201** with the object. PUT returns **204** and copies **only `spec`** onto the stored object (`current.Spec = r.Spec`; labels, annotations and the name cannot change). DELETE returns **204**, also for a missing object: the handler's Get fails with NotFound, and the error handler answers NotFound on a DELETE with 204 (`error.go:144-152`).
- **Strict request bodies.** `BindJSON` calls `DisallowUnknownFields` (`base.go:216-230`), and the bodies decode into the controller's own Go types at the version the Hub pins (`go.mod:19`, `agentic-controller/api` @ `38046470`). Any field that version does not know is a **400**. That pin, not controller `main`, is what `contract.ts` and the adapters must match; the fields listed under [Contract drift](#contract-drift) are all present at the pin.
- Workflow runs and agent runs have no PUT. On create the Hub mints a token Secret, adds it as `envFrom`, and appends `HUB_BASE_URL` to `spec.env`. The client sends `APP_ID` and `TARGET_BRANCH` in `spec.env` and the `konveyor.io/application` label (`createAgentRun` / `createWorkflowRun` do this).
- Errors: a k8s NotFound becomes 404 (204 on DELETE) and a body bind error becomes 400. Other k8s errors (AlreadyExists, Invalid from CRD validation, Forbidden for the Hub's ServiceAccount) fall through to **500** with the k8s message. `utils/agentic.ts` `isAgenticRbacError` detects the RBAC case.
- The Hub does not check references: deleting an Agent used by a workflow, or a SkillCard used by an Agent, succeeds.

## 4. Entity and field mapping

General rules:

- `id` ↔ `metadata.name` (DNS-1123: `^[a-z0-9]([a-z0-9.-]*[a-z0-9])?$`). The name is chosen by the client on create and cannot change. Runs use `generateName: "ui-"`.
- `name` (display) ↔ `metadata.name`, except SkillCard (`spec.displayName`). `toResourceName()` slugs display text into a resource name.
- `EntityRef` ↔ a bare name: `{ ref }`, `agentRef`, `workflowRef`, `skillCardRef`. The adapters build refs whose `name` is the id unless you pass a `NameIndex` (`toNameIndex(domainEntities)`).
- `createTime` ↔ `metadata.creationTimestamp`. `updateTime` has no source.
- Updates: the Hub replaces the whole `spec`, so every `to*Spec` writer takes the current spec as `base` and spreads it (stage and parameter entries too), so CRD fields the domain does not model, including fields a newer controller adds, survive a save. `real-samples.test.ts` round-trips every controller default and sample CR (fixtures: `agentic/adapters/__fixtures__/agentic-controller-369070c6/`, verbatim from that commit).
- Names: create with `toNewResourceName(name)`; before an update call `assertNotRenamed(id, name)` (see [C](#c-names-are-immutable)).
- Operator-owned objects: `Agent`, `Skill`, `SkillCollection` and `MigrationPlan` have an optional `operatorManaged` (label `app.kubernetes.io/managed-by: agentic-controller-defaults`, `utils/agentic.ts` `isOperatorManaged`). ### Skills attached from the other side

Five endpoints let the entity a skill is attached to (or the collection or agent) edit what is attached to it. Each
replaces the whole set for one entity with body `{ skills | collections | agents: IdRef[] }` and answers 204. The
shape follows the Hub's `PUT /applications/:id/tags` (a per-entity sub-resource whose PUT replaces the set;
`internal/api/application.go`) and the existing prototype nesting `PUT /archetypes/:id/target-profiles/:id/plan`.
Reads need no new endpoint: an entity's attached Skills are the Skills whose `associations` contain
`{ scope, resource.id }`, a Skill's collections are the collections whose `skills` contain it, and a collection's
Agents are the Agents whose `skillCollections` contain it (the reverse lookups of section 5).

| Prototype route                                         | Stored as (mock)                                 | Real backend                                                                 | Invalidates as    |
| ------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------- | ----------------- |
| PUT `/archetypes/:id/skills`                            | `Skill.associations` rows with scope `archetype` | none: proposed Hub join table (SkillCard name, scope, Hub resource id)       | `skill`           |
| PUT `/archetypes/:id/target-profiles/:profileId/skills` | rows with scope `targetProfile` (profile id)     | same table                                                                   | `skill`           |
| PUT `/applications/:id/skills`                          | rows with scope `application`                    | same table                                                                   | `skill`           |
| PUT `/skills/:id/collections`                           | `SkillCollection.skills`                         | `SkillCollection.spec.skills[].skillCardRef`, one PUT per changed collection | `skillCollection` |
| PUT `/skill-collections/:id/agents`                     | `Agent.skillCollections`                         | `Agent.spec.skillCollections[].ref`, one PUT per changed Agent               | `agent`           |

- **Same rows both ways.** The mock edits the rows `GET /skills`, `/skill-collections` and `/agents` already read,
  so the skill form's `PUT /skills/:id` (with `associations`), the collection form and the agent form see the change
  on the next read, and the plan, application and run resolutions follow. Only
  `PUT /skills/:id` sets the Skill's `updateTime`: an edit from the entity side (these five PUTs) leaves it as it is,
  and the proposed join table would behave the same, since its rows are not part of the SkillCard.
- **Plan skill review.** The plan skill resolver (`POST /plans/skills/resolve`, `GET /skills/:id/plans`; see
  [Plan skill resolution](#plan-skill-resolution-resolveplanskillsrequest--skillsbystage-skillplan)) reads the same rows.
  Archetype and target profile attachments made here show in the wizard's Skills step, on the plan page and in the
  skill page's "Used in migration plans", and can be excluded there. Collection memberships and collection Agents
  change the collection origins of the stages whose Agents use the collection. Application attachments reach only
  runs, the application Skills and Migration tabs and the Run migration plan dialog (source 5). There a plan's
  exclusion applies while the plan still resolves the skill (section 7 item 7). All five PUTs invalidate
  `planSkills`, `skillPlans` and `applicationMigrations` through `MUTATION_EFFECTS`.
- **Prototype scenarios.** The three Hub-scope PUTs only see the Skills that `GET /skills` returns in the current
  scenario. In `initial`, which hides the fixture Skills, they leave the fixture rows as they are and answer 400 for a
  fixture Skill id, so switching back to `configured` shows the fixtures unchanged. Mock only: the real backend has no
  scenarios.
- **Hub scopes.** The Hub has no storage for skills attached to archetypes, target profiles or applications (section 7
  item 7). Proposal: one Hub DB join table with cascade on archetype, target profile and application delete, served
  both as `associations` on the Skill view and as these sub-resources. A DB write makes the entity-side PUT one
  transaction, unlike the CRD fan-out. Runs only load these Skills once the controller or Hub passes them to the run
  (the controller reads Skills from the Agent only). `agentic-hub.ts` leaves these three functions out.
- **Fan-outs.** `agentic-hub.ts` `updateSkillCollectionMemberships` and `updateSkillCollectionAgents` read every
  collection (or Agent), check every change first, then PUT each changed object in turn, as `writeAgentAssociations`
  does for the skill form. Not atomic: a failure mid-way leaves earlier objects written, so re-fetch and report a
  partial failure. Last write wins: the Hub ignores the client `resourceVersion`, so a concurrent collection or agent
  form save can overwrite the change.
- **Errors.** 404 for an unknown entity in the URL (archetype, target profile within its archetype, application,
  Skill, collection), 400 for a bad body or an unknown referenced id (as the existing writes do), 409 when a
  collection or Agent that would change is `operatorManaged` (the operator reverts it; the prototype never sets the
  flag). `PUT /skills/:id/collections` answers 400 naming the collection when the Skill is its only member, because
  the SkillCollection CRD needs at least one `spec.skills` entry. Every refusal rejects the whole request with no
  partial change. The fan-outs throw for the same cases, plus a member provided by an `image`/`source` entry and a
  collection that enumerates `spec.image`, before any PUT. The forms show the response `message` as is in their
  partial-failure toast, so the mock words it in the UI glossary ("{name} is managed by Konveyor and cannot be changed
  here.", "{skill} is the only skill in {collection}. A skill collection needs at least one skill."); the real server's
  message is shown unchanged. The `agentic-hub.ts` fan-outs throw with the same wording.
- **Unknown is not none.** The Manage skills modal never reads an undefined `associations` as "no skills": when
  any Skill lacks it, the modal shows "Attached skills are not available. Try again later." with Close only and
  refuses to save, because the replace PUT would drop attachments the UI cannot see.
- **Real adapters today.** `agentic-hub.ts` `getSkills` passes the Agents, so `associations` is defined but holds
  agent-scope rows only. That guard therefore does not trigger: the modal opens with an empty direct set, and Save
  calls one of the three functions `agentic-hub.ts` leaves out. The skill form's archetype, target profile and
  application pickers likewise start empty and `updateSkill` refuses a selection. Until the Hub serves Hub-scope
  attachments, the six Manage skills placements and those three pickers are not usable; see wiring checklist step 8.

How the migration plan pages read these fields:

- **Assigned means the default plan.** A plan is _assigned_ to a target profile when its `migrationPath.isDefault` is true
  and the profile is in its path; only assigned plans resolve to applications (`resolvePlanFor`). The plan page lists every
  target profile of the path and, when `isDefault` is false, says "Not assigned. Applications get this plan once it is
  assigned." with a link to the archetype's target profiles page. Archetype surfaces show only the assigned plan.
- **Server-derived fields need Hub support.** With the real adapters `migrationPath` and
  `applicationImpact` are undefined, and `runCount` is undefined unless runs are passed. The UI treats undefined as unknown,
  never as empty: Applications, Runs and Skills by stage read "Unavailable" (Target profiles on the plans list and the
  plan page read "Not assigned": the prototype treats an absent `migrationPath` as a plan that runs when someone picks
  it), and Delete is
  disabled with "Usage could not be checked. Try again later." A plan without a migration path is not a configuration
  issue (it runs when someone picks it), so the configuration checks are "Stages have agents" and "Models verified"
  only: no path alert, no list marker for it. Skills by stage therefore only works
  once the Hub serves these fields (7.2, 7.7).
- **The plan's applications.** `applicationImpact.applications` (optional, additive) lists the applications counted
  in `matching`: those whose migration view resolves to this plan, in name order. The plan page counts them, and
  "Run migration plan" on the plans list and the plan page runs exactly these applications. A server that only counts
  them leaves the field out; the UI then shows the count and disables the run with a reason. The Hub needs the same plan
  resolution it needs for `matching` (7.2). The run starts `planSelection: "single"` with the plan's id and the
  applications the user keeps selected in the dialog (`StartApplicationMigrationsRequest`, unchanged). PatternFly
  hard-codes the selection checkbox names ("Select row n", "Select all rows"); the Application cell is the row header, so
  it names each row, and the checkboxes should not be replaced with custom ones to rename them.
- **Target profiles on the plans list and plan page.** Both show a plan's archetype + target profile pairs
  ("Quarkus 3.x (Java EE Application)"), derived client-side from `migrationPath` by `getPlanTargetProfiles`
  (`projection.ts`): the list shows the assigned pairs only (`isDefault`, `getAssignedTargetProfiles`), and its Archetype
  filter matches them; the plan page shows every pair of the path. In the intended model the reference is on the target
  profile: one archetype has several target profiles, and several profiles, across archetypes, can use one plan.
  `migrationPath` (one archetype) cannot express that, and `assignPlanToTargetProfile` replaces the path when a plan is
  assigned to a profile of another archetype. Backend need: a migration plan ref on Hub `TargetProfile` (like
  `analysisProfile`); the client then derives each plan's pairs from `GET /hub/archetypes` (profiles are inline) with no
  new query, or the server returns a derived list of target profile refs on the plan. Only `getPlanTargetProfiles`
  changes on the client.
- **Skill review.** The wizard and the plan page resolve a plan's skills per stage with `resolvePlanSkills`, which includes the
  agents' collection skills, and the skill page lists the plans that resolve a skill with
  `getSkillPlans`, from the same resolver. With the real backend the call is unwired (7.7, checklist step 8)
  and the adapters leave `excludedSkills` undefined; `toWorkflowSpec` drops it on save.
- **Open questions, not designed around:** plan names are immutable in the Hub (`assertNotRenamed`, [C](#c-names-are-immutable))
  but the wizard keeps Name editable; "Require approval after this stage" maps to `execution.mode: approve`, which gates
  tool calls inside the stage rather than the stage boundary ([A](#a-approvals-happen-inside-a-live-session-and-are-denied-when-nobody-is-watching)),
  and the checkbox copy stays; whether editing a plan changes runs already in progress is unanswered, so the delete
  confirm and the edit Review say nothing about it.

### Plan runs by archetype

The plan runs list has an Archetype filter and names each run's archetypes under its applications; the archetype
drawer's Details tab has a "Plan runs" count that opens the list filtered by that archetype
(`archetypePlanRunsLocation`). No data-layer change: it is a client join of `GET /plan-runs` with Hub `GET /archetypes`.

- **Rule** (`runTouchesArchetype` in `utils/agentic.ts`, shared by the filter, the list and the count): a run belongs
  to an archetype when any of its applications is in `archetype.applications`. It does not use the plan's
  `migrationPath`: a plan without a path, or one plan run on applications of several archetypes, still counts for each
  archetype involved.
- **Current membership, not a snapshot:** an application re-tagged into another archetype moves its earlier runs with
  it, the same as the inventory's Archetypes filter. Recording the archetypes on the run at start (a label or a
  `status` field on `AgentWorkflowRun`) would fix that; not needed now.
- **Real backend:** the client join works while the list is read whole. If runs are ever paginated or filtered on the
  server, the run list needs an `archetype=<id>` query parameter with the same rule (runs labeled
  `konveyor.io/application` with a member application), and a count per archetype for the drawer.
- **Polling from the drawer:** today the drawer's count reads the whole run list (`useFetchPlanRuns`, shared cache with
  the plan runs list), which polls every 5 s while a run is active (30 s when every active run awaits approval) for as
  long as the archetype's Details tab is open. Fine at prototype scale; a real backend should serve the count per
  archetype instead of the drawer polling the full list.

   resolver (`resolvePlanSkills`), which includes collection skills.

   **Skill review and exclusions** (`resolvePlanSkills`, `MigrationPlan.excludedSkills`, `StageSkill.excluded` in
   `PlanRun.skills` and `ApplicationMigrationView.skills`): the real backend has no exclusion, override or preview for skills, and
   resolves a run's skills only from the stage Agent's `spec.skillCards` and `spec.skillCollections`, when each stage's
   AgentRun starts (`resolveSkillVolumes`); archetype and target profile sources exist only in the prototype. The mock
   shapes follow a proposed additive backend field, modelled on stage `execution` (ADR 0018): per stage, `AgentWorkflowStage.skills.exclude[]`
   `{ ref, reason? }` (keyed by SkillCard name, the controller's staging name), snapshotted into
   `AgentWorkflowRun.status.stages[].skills` and stamped on `AgentRun.spec.skills`; the UI's plan-level exclusion writes
   the same entry on every stage, and an exclusion that matches nothing should be a warning, not a failure. An exclusion
   is per plan and by skill, and applies to every origin except the application itself: a skill attached to the
   application is never excluded (the most specific attachment wins). Excluded skills stay listed
   with `excluded: true`, so the stage tables show them. An exclusion of a skill that reaches nothing excludes
   nothing; the wizard drops the stored entry on the next save. The preview
   is a proposed Hub endpoint, `POST /hub/agentic/workflows/skills/resolve` with a draft `AgentWorkflowSpec` (and,
   optionally, applications), returning `SkillsByStage`: per stage the skills with their origins (`via` paths) and
   `excluded`, plus the context skills once per application. What a run actually mounted
   is agentic-controller#172 (`status.skillSources`, `status.skills`). `GET /skills/:id/plans` (`SkillPlan[]`) is the
   same resolution for every saved plan, keyed by the skill; propose it with the resolve endpoint (for example
   `GET /hub/agentic/skills/:name/workflows`). Without them, a production build sends both calls to
   `/hub/prototype/agentic/*` and gets 404. A 404 or 501 from either endpoint reads as "not served"
   (`isResolveEndpointMissing` in `queries/agentic.ts`): the wizard's Skills step shows the informational "This
   server cannot preview the skills of a migration plan." (body "You can still create the plan." or "You can still
   save the plan.") with no Try again, the plan page's Skills by stage says "Unavailable" and "This server cannot list the
   skills of a migration plan.", the skill page's "Used in migration plans" says "This server cannot list the
   migration plans that use this skill.", and the wizard Review reads "Unavailable". Other failures (any other status, or no response) keep the danger
   alert with Try again in the wizard and on the plan page's Skills by stage (wiring checklist step 8). The resolve request
   is sent as the caller builds it, stages in stage order; only the query key is normalized.
   In the `initial` scenario `POST /plans/skills/resolve` hides nothing, like a saved plan's resolution: Hub
   archetypes and target profiles are not scenario-aware, so a draft with an archetype resolves the fixture skills
   attached to it, while `GET /skills` hides them and `GET /skills/:id/plans` and their pages are 404.
   `PUT /plans/:id` replaces `excludedSkills`: a body without it clears the plan's exclusions. POST and PUT
   `/plans` drop `excludedSkills` ids that are not skills (a skill deleted after the wizard resolved), as the resolve
   endpoint does, and answer 400 only for a malformed value; reads drop the exclusions of deleted skills. The backend
   should do the same: an exclusion that matches nothing is a warning, not an error.

   **Run exclusions and the target profile pick**: see [Run skill review](#run-skill-review-target-profile-pick-and-run-exclusions).

8. **Run results** (`ApplicationMigrationResult`, stage `commits`). Part of this is in ACP plan-entry `_meta` (`konveyor.io/plan`, see `acp.ts` `PlanRungMeta`).
9. **Descriptions and display names** for Agent, Gateway, AgentWorkflow and SkillCollection (no CRD field; the forms have free-text names such as "Java EE to Quarkus"). Options: slug names (`toResourceName`) plus a display-name annotation, or new spec fields.
10. **Rename**: `metadata.name` is immutable and the Hub copies only `spec` on PUT, so editing a name is impossible except a SkillCard's `displayName`. The forms allow renaming; the adapters refuse it (`assertNotRenamed`). See [C](#c-names-are-immutable).

### Semantics that differ

11. **Approval granularity and timing**: the prototype approves a stage, at any later time; the backend approves tool calls (ACP `session/request_permission`) inside a stage whose `execution.mode` is `approve`, only while someone is attached, and denies otherwise. `ControllerRunPhase` still contains `AwaitingApproval`; a pending approval should be `intervention`, separate from phase. See [A](#a-approvals-happen-inside-a-live-session-and-are-denied-when-nobody-is-watching).
12. **One run per application**: the prototype groups several applications in one plan run; the controller runs one AgentWorkflowRun per application. Plan run list and detail pages show `applications[]`. Known gap: because the prototype's run is shared, an approve or reject from one application's Migration tab (`POST /application-migrations/:appId/requests/current`) decides for every application in that run. The UI says so and names every affected application in a confirmation; with the backend's per-application runs the decision becomes per application and that wording can go. See [D](#d-one-workflow-run-per-application).
13. **Reject**: no reject endpoint; deny the ACP permission or delete the run.
14. **Required CRD fields the UI cannot supply**: `Agent.spec.image`; `Gateway.spec.credentialRef` (a k8s Secret, while the form picks a Hub identity) and `spec.model.contextWindow`; a run's `spec.gateway`, `TARGET_BRANCH` for test runs and required parameters ([B](#b-runs-need-inputs-the-ui-does-not-collect)). The forms need these fields, or the Hub needs defaults. The UI has no API to create the credential Secret.
15. **Referential integrity**: the Hub deletes referenced resources without a 409, and returns 500 for AlreadyExists and CRD validation errors. Duplicate-name and in-use messages the mock gives as 409 will arrive as 500 with a k8s message; nothing maps those messages to form errors yet.
16. **Managed-label filter**: `GET /agentic/agents` and `/agentic/workflows` list only `konveyor.io/managed=true` (the Hub adds it on create; the shipped defaults carry it). Objects the operator owns (`app.kubernetes.io/managed-by=agentic-controller-defaults`) revert edits; the adapters expose this as `operatorManaged`, and `managedActionProps` (`utils/agentic.ts`) disables Edit and Delete for them with a tooltip.
17. **Gateway "verified" vs usable**: `VerificationSkipped` makes a Gateway Ready but unverified; `VerificationStatus` has no value for that (the adapter maps it to `verified` with the message in `statusReason`).
18. **Model form depends on Providers**: the Model form picks its provider from `useFetchProviders` (missing backend) and its model from `useFetchAvailableModels` (missing). Wiring Models alone still needs a decision on Provider (section 4).
19. **Conditions not in the domain**: Agent Ready / `GatewayConfigured`, AgentWorkflow Ready (`AllAgentsReady`), SkillCard `type` and `Resolvable`, Gateway `contextWindow` and `tier`. Add them to the domain types when a page needs them.

### Prototype data-layer items (not fixed here)

20. Hooks and types still say Gateway (`useFetchGateways`, `Gateway`) while the REST functions and UI say Model.
21. Execution policy: `getExecutionPolicy` / `updateExecutionPolicy`, the `executionPolicy` query group and its `MUTATION_EFFECTS` entry remain for the mock (whose default is `interactive`), but no hook or page uses them.
22. `useFetchAgentTestRuns` assumes a server-side `agentId` filter, and `useFetchPlanRuns` a `planId` filter. With the real API, filter client-side and exclude stage AgentRuns (`isAgentTestRun`), as `agentic-hub.ts` does.
23. The mock serves migration views only for its 13 portfolio applications, and resolves applications from mock data even with `MOCK=stub=agentic.pass`.
24. Run application names: the adapters name a run's application `#<id>` unless given an `ApplicationNameIndex`; join `useFetchApplications` in the hook. A test run with no application maps to `{ id: 0, name: "" }`, and a run with no timestamps to `startedAt: ""`.
25. `PlanRun.startedAt` is set even while the run is Pending (the mock fills it at creation; the adapter falls back to `creationTimestamp`). The UI does not read it as a start: a Pending run shows "Not started" for Started and Duration in the plan runs list, and "Waiting to start" in its run page status line with "Not started" for Duration (`planRunDurationSeconds` in `utils/agentic.ts`). A server that leaves it unset until the run starts would match the UI better.
26. Fixture oddities, rendered as the server returns them: Run #7's awaiting stage has no messages, so its duration (and the run's) reads "Unavailable": the clock of a stage awaiting approval stops at its agent's last message. Fixed by the skills data change (see [Skills data changes](#skills-data-changes)): hand-written run skills snapshots (Run #1 listed Customer Management, which is not in the configured-world run, and no agent or collection sources), applications on plans of other archetypes, and run messages naming applications that are not in the run.
27. Run names are opaque. The mock names a run "Run #{n}: {plan name}" (colon, like "Stage {n}: {stage}"); the UI never relies on it and always reads the plan from `planId`/`planName`.
28. Stage output is shown verbatim, so mock copy shows through: the `awaitingStage` message in `execution.ts` says "…ready for architect review. Awaiting your approval to continue.", which names a persona and says "your approval" to people who may not be able to approve. Suggested mock text: "Analysis complete. Migration proposal ready for review." In the failed scenario the stage `output` equals the last activity message, so the same sentence appears in the alert, the Activity table and the output block; real multi-line controller output does not repeat like this (the alert shows only its first line, the block is collapsed). The plan 1 "Migrate" instructions say "previous Stage" with a capital, and are rendered as written.
29. `StageMessage` has no author: a `role: "user"` message reads "User" in the stage Transcript tab. A server that names the user would let the UI say who (or "You").
30. Open question: how is "Review before start" (`preflight: "reviewRequired"`) resolved? The preflight dialog has no confirm action and the domain has no confirm endpoint, so such an application can only be excluded from a start today.
31. `ApplicationMigrationView.action` (`ApplicationMigrationAction.title`, `description`, `risk`, `requestedAction`) is intentionally not rendered. The Migration tab's attention alert composes its copy from the run instead (the stage awaiting approval, its agent and the next stage), the same alert as the plan run page, so a decision reads the same everywhere. A backend may keep sending the field; the UI ignores it.

### Run observability

32. **Approve mode and askUser runs are never recorded** (hub branch recorder gate, kept by [#341](https://github.com/konveyor/agentic-controller/issues/341)): exactly the runs a human interacted with have no transcript, only logs, the resource and usage. The UI shows the stage's `StageRun.messages` (from the live session) in their place, so wire step 7 before relying on this view for approve mode stages. Permission asks and their answers are not in any transcript either.
33. **Cost is never filled**: the harness reads `cost.amount` from goose's custom channel, which sends `accumulatedCost`; `terminationData.usage.cost` and `maxCost` enforcement are affected ([PR 282](https://github.com/konveyor/agentic-controller/pull/282) section 2). Tokens are discarded the same way.
34. **Usage only at the end today**: `terminationData.usage` is written once, when the pod terminates, and dropped by the 4 KiB fallback. Live usage needs the ACP stream (`usage_update`) or a recorded transcript. Typed `status.usage` on AgentRun and stage is proposed only (ADR 0021, PR 282). The mock reports full usage for every stage, as ADR 0021 would.
35. **No upstream logs or transcript endpoint**: pod logs vanish with the pod (TTL or cascade), transcripts live only in goose's in-pod SQLite. The `/logs` and `/transcript` endpoints exist only on the observability hub branch.
36. **#341 serving is undecided**: hub proxy, pre-signed S3 URLs or a controller-served API; recording status fields on the CR (`status.recording`, `skipReason`, `gaps[]`) are examples in the issue, not a schema. Keep byte offsets for logs and line offsets for transcripts whichever is chosen.
37. **Prototype simplifications**: the mock transcript route returns the folded transcript (not NDJSON) and the whole of it on each poll; the mock never answers 404 for a started stage, while the hub does in its first seconds (covered by the hook tests). The log is already incremental: `useAgentRunLogs` keeps the complete lines and the partial last line apart and splits only new text, and the Logs view prefixes ("All containers") and expands tabs only for the lines that changed; LogViewer itself still reparses its whole `data` on each update. The stage agent runs share the `/agent-runs` prefix with agent test runs (both are AgentRuns), and an agent test run name answers 404 there.

## 8. Wiring checklist

Do these in order; each step leaves the app working.

1. **Reach the Hub.** You need a cluster with Agent Sandbox, an agentic-enabled Hub, the agentic controller and its defaults, a credential Secret and at least one Gateway: follow agentic-controller `docs/getting-started.md` sections 1 to 4 (`docs/local-minikube-setup.md` in this repo does not cover agentic). Then run `MOCK=stub=agentic.pass AUTH_REQUIRED=true npm run start:dev` (it already runs `npm run port-forward`; do not start a second one). Confirm `GET /hub/agentic/agents` works with your token and that the WebSocket upgrade for `/hub/agentic/` passes the proxy (`server/src/index.js`).
2. **Refresh the contract.** Update `api/agentic/contract.ts` to the controller API the Hub pins (`go.mod`; `38046470` today, see [Contract drift](#contract-drift)). Re-copy the controller's `config/defaults` and `config/samples` into `agentic/adapters/__fixtures__/` from the same version and rerun `real-samples.test.ts`.
3. **Decide the open questions.** [Design questions A to D](#design-questions-blocking-backend-integration), and section 7 items 9, 14 and 18: display names and descriptions, rename, where `image`, `credentialRef` and `contextWindow` come from, how a credential Secret gets created (the UI has no API for it), the run Model, and Provider. Add the form fields or Hub defaults.
4. **Swap the catalog reads.** Move the read functions from `api/rest/agentic-hub.ts` into `api/rest/agentic.ts` (`getSkills`, `getSkillById`, `getSkillCollections`, `getSkillCollectionById`, `getModels`, `getModelById`, `getAgents`, `getAgentById`, `getMigrationPlans`, `getMigrationPlanById`). They make extra fetches for joins: Skills fetch the Agents, Agents and collections fetch every SkillCard for names, Plans fetch every workflow run for `runCount`. Decide whether joins stay in the REST function or move into hooks (shared cache, fewer refetches while polling). Update the page tests that stub `AGENTIC_ENDPOINTS` (section 2).
5. **Swap the catalog writes.** Move the create/update/delete functions over. Each update calls `assertNotRenamed`, fetches the current object, then writes `to*Spec(request, current.spec)`. Add a helper that maps the Hub's 500 messages (AlreadyExists, Invalid, Forbidden; `isAgenticRbacError`) to form errors. `createModel` and `createAgent` wait for step 3. Render `operatorManaged` objects read-only.
   Also move `updateSkillCollectionMemberships` and `updateSkillCollectionAgents` (fan-outs over the collection and Agent PUTs; see [Skills attached from the other side](#skills-attached-from-the-other-side)).
6. **Swap runs.** Move `getPlanRuns`, `getPlanRunById`, `getAgentTestRuns`, `startAgentTestRun` and `startApplicationMigrations` over (single-Plan only until resolution exists). Collect the run Model, target branch and parameters first ([B](#b-runs-need-inputs-the-ui-does-not-collect)); runs of the shipped workflow fail without a Model. Settle partial failure of multi-application starts and the run grouping ([D](#d-one-workflow-run-per-application)). Join application names in the hooks.
7. **Approvals over ACP.** Only after [A](#a-approvals-happen-inside-a-live-session-and-are-denied-when-nobody-is-watching) is decided. Port a session hook from upstream `ChatPanel.tsx` over `api/agentic/acp.ts` (`mintAcpNonce`, `getAgenticAcpUrl`); dial only while the AgentRun's `ACPReady` condition is True; gate on `agenticAcpScopes`. The approval mutations then take the AgentRun name, the permission request id and the option id; `AwaitingApproval` goes.
8. **Gate what the backend does not serve.** MSW is not in production bundles, so a production build with `AGENTIC_ENABLED=true` sends every call for a missing group to `/hub/prototype/agentic/*`, which no Hub serves. The affected surfaces:
   - application migrations: the inventory Migration column, attention alert and Run migration plan (`applications-table.tsx`), the Migration tab (`migration-tab.tsx`), the start dialog (`migration-preflight-modal.tsx`, `use-start-migrations.tsx`);
   - Providers and available models: Administration > Providers (`providers.tsx`, `provider-form.tsx`) and the Model form (`model-form.tsx`);
   - the organization default Model (`models.tsx`, "make default");
   - Plan migration paths: Assign/Change migration plan on the target profiles page (`assign-migration-plan-modal.tsx`), the wizard's path step (`plan-wizard.tsx`), the Target profiles column and fact in `plans.tsx`, `plan-details.tsx` (pairs from `getPlanTargetProfiles`), the Skill form's archetype and profile scopes;
   - plan skill review: `useResolvePlanSkills` (the wizard's Skills step and Review, the plan page's Skills by stage, and the Run migration plan dialog's Skills by stage, which sends `applications` for every run it previews except one application on its own plan, whose migration view already carries `skills`; while the endpoint is not served the dialog shows "Unavailable" with "You can still run the migration plan." and Run stays enabled), `useFetchSkillPlans` (the skill page's "Used in migration plans") and the `excludedSkills` rows on plan, run and application pages, until the Hub serves the resolve endpoints and the CRD has stage `skills.exclude` (7.7). While the endpoints are not served (404 or 501), the wizard's Skills step, the plan page's Skills by stage and the skill page section already show an informational "not available" state without a retry; hide them instead if that reads better. When the Hub serves them, write a plan-level exclusion into every stage and read the run's exclusions from its snapshot;
   - approvals (`plan-run-detail.tsx`, `stage-run-detail.tsx`, `migration-tab.tsx`) until step 7.
   - Hub-scope Skill attachments: the "Manage skills" actions on archetypes, target profiles and applications
     (`updateArchetypeSkills`, `updateTargetProfileSkills`, `updateApplicationSkills`) until the Hub join table ships
     ([Skills attached from the other side](#skills-attached-from-the-other-side)).
     Decide one: (1) hide the Manage skills actions (gate `useCanManageSkills`) and the skill form's archetype, target
     profile and application pickers until the join table ships, or (2) ship the join table first, served both as
     `associations` on the Skill view and as the three PUTs. Shipping `associations` alone is not enough: the modal
     would show the right set and fail on Save. **Recommended: (1)**, as a capability entry in option (b) below, so
     the real adapter never shows an empty set as the truth.

   Options:
   - **(a) Do not enable in production until everything is wired.** Keep `AGENTIC_ENABLED` off in production builds. Simple and safe, but nothing ships until the last missing group has a backend.
   - **(b) A capability map in code.** One module (for example `agentic/capabilities.ts`) exports which groups the backend serves; routes, sidebar entries, table columns and actions check it next to `isAgenticEnabled`. Flip an entry when its backend ships in the Hub version the UI is released with.
   - **(c) Per-capability environment flags.** Like (b), but each entry comes from `window._env` (`AGENTIC_<GROUP>_ENABLED`). Only worth it if one UI build must run against Hubs with different agentic API levels.
   - **(d) Runtime detection.** Probe each group (404 or 405 means missing) and hide it. Adds a request and a loading state per surface, and turns a misconfigured proxy into a silently hidden feature.

   **Recommended: (b).** The operator installs the UI with a matching Hub, so what the backend serves is a property of the release, not of a deployment; a typed map keeps the gating explicit, testable and greppable, with no new configuration surface. Move the missing groups' paths into their own `AGENTIC_ENDPOINTS` group so the split is visible. Until a group is gated, it must stay unwired and its surfaces hidden: never rely on the mock in a build that can reach production.

9. **Mocks in CRD shape (recommended).** Make MSW serve CRD objects at `/hub/agentic/*` for the swapped groups (reuse the fixtures through reverse mappers), so local development and the e2e suite run the same adapters as production. Without it, every swapped group loses its mock.
10. **Clean up.** Strip the prototype shell (section 1), remove `AwaitingApproval` from `ControllerRunPhase`, rename the Gateway hooks and types to Model, keep one set of agentic scope constants, and move configuration checks to conditions (section 5).
11. **Verify.** `npm test -w client` (adapters: `client/src/app/agentic/adapters/{adapters,real-samples}.test.ts`; Hub module: `client/src/app/api/rest/agentic-hub.test.ts`). The Playwright suite in `e2e/` is prototype-only (it drives the mock through `protoScenario` / `protoPersona`); against a real cluster, test by hand or write new specs, including Hub errors (RBAC 500, missing objects, operator-managed objects, runs without a Model, denied approvals).
12. **Run observability** (after step 6). Replace `getPlanRunAgentRuns` with the workflow run read plus GET `/agentic/agentruns/:name` per started stage (for a plan run on several applications, of every application's workflow run, in the run's application order), mapped by `toStageAgentRun(run, { runId, stageId, phase: stage.phase, gateway, applicationNames })`; `getAgentRunResource` with the plain AgentRun read. Once a logs and transcript endpoint exists ([#341](https://github.com/konveyor/agentic-controller/issues/341); the observability hub branch is the model): `getAgentRunLog` reads the body from `?offset=<bytes>` as bytes and returns `{ text, offset, nextOffset: offset + byteLength, source: X-Log-Source, complete: false }`, decoding with a streaming `TextDecoder` kept per log (or cutting at the last newline) so a chunk that ends inside a character does not garble it; `getAgentRunTranscript` fetches NDJSON and returns `{ status: X-Transcript-Status, skipReason: X-Transcript-Skip-Reason, entries: foldTranscript(parseRecordedTranscript(body)).entries }`. Let both reject a 404 (axios does): the hooks read it as "not there yet" while the stage is not terminal (an empty log, a `none` transcript, polling on) and, once it ended, as "no log for this container" and "not recorded". Polling needs no completion signal from the server: every hook reads once more after the stage turns terminal and then stops. Hooks keep their signatures. Without a live usage source a running stage has no usage until its pod ends (item 34): the context row and the usage facts say "Not reported yet" (decided from the readings, not from a time), so nothing promises an update. For live usage before ADR 0021 lands, fold the transcript's `usage` (or a live ACP session through `TranscriptFolder`) into `liveUsage`. Then rerun step 11.
